## 已认可的三阶段方向

1. **Phase 1：先稳住现有星空。** 修复打包和依赖，整理数据、状态与生命周期，停止不必要的持续力模拟，建立能重复测量的性能基线。保留现有词库、功能和学习记录。
2. **Phase 2：只加载和展示当前需要的词。** 先显示词根或区域概览，再按需读入区域、词根与单词；布局在构建时预先算好。词库源文件继续作为人工维护入口。
3. **Phase 3A：成批绘制星星和关系线。** 在 Phase 2 已稳定的数据、布局和场景接口上替换渲染方式，完成正确性、性能、故障恢复与发布验收。
4. **Phase 3B：在证据充分后删除旧方式。** 这是独立的未来发布步骤，不能在初次实施时提前做。

三个阶段按顺序推进，每个阶段都应有可运行版本、验证和回退方法。可让多个智能体并行做独立审计、下一任务预检和互不冲突的小任务；共享接口与有先后依赖的实现不能同时乱改。

## 实现时必须保留的约定

- 词根、单词、词间关系及原主要学习操作保持兼容，不借性能改造重做视觉主题或学习内容。
- 进度主键保持 `star-vocab-progress-v1`，内容保持 `Record<string, Progress>`，包含已有的 `srs` 字段；不因渲染重构而丢失或暗改用户记录。
- 词根和单词可能共享原始 ID，例如 `scope`。场景使用 `root:<id>`、`word:<id>` 等带类型的稳定键，进度仍使用原 word ID。
- `SceneCoordinator` 是唯一负责 3D 状态订阅、数据和场景切换生命周期的模块。Renderer 不直接读 React、Zustand 或 repository；只接收固定的场景、命令和变更接口。
- 场景更新保留 epoch、取消信号、暂存资源和原子提交；过期请求不能覆盖新场景，失败时要保留上一个有效场景。
- 静态备用界面和 3D 使用同一份经过校验的数据与导航语义，不能为故障回退再造第二套状态来源。
- 私人配置与原聊天历史不上传公开仓库。项目通用配置与本机专用配置分别保存；已有本机资料先保留，再按新机路径调整。
- 本项目迁移与运行不需要 fal 密钥。除非用户针对当前任务明确指定使用该密钥生成，不发起任何 fal 请求。

## 已知限制与验收门槛

原计划基线发现两份 Three.js 运行时、打包类型错误、持续力模拟、逐个对象绘制、全量 3D 首屏加载及清理不完整等问题。本次只做让项目能备份与恢复的补齐，不能将这些整体问题视为已经解决。

性能目标目前都是**待验证的目标**。例如 Phase 1 要验证 120 KiB 初始 JS / 430 KiB 全部 JS 的 gzip 预算、各首屏时间、三个场景中位 FPS 至少 50、帧间隔、交互反馈、100 次进度写入与资源清理。当前构建可能仍提示 JS 块较大；实际数字和是否通过必须由正式报告证明。

Phase 1 进入 Phase 2 的条件包括构建、功能、bundle、浏览器、视觉、生命周期、有效 D1/D2 性能、相对基线、持久化和回退验收全部通过，且 `verify:phase1-release` 成功。普通本地诊断不等于正式性能验收。原环境缺少 Android 真机工具时记录 `skipped: no-adb`，不得造出手机通过结果。

Phase 2 完成后，必须通过完整的真实 Pixel 7a D3 门槛及 Phase 2 发布验收，才能进入 Phase 3A。桌面模拟手机视口不能代替这次真机验证。

Phase 3B 必须等待两次连续稳定发布，覆盖至少 14 天；完整 D1/D2/D3 矩阵零失败、回退演练、旧版本与旧数据保留 30 天、计划要求的签名与证据校验都通过后，才可在独立未来发布中删除 Legacy。不能因测试通过、时间难等或原计划已有步骤就提前删。

原计划里提到的执行技能以接续环境中实际可用的工具为准；找不到旧技能时，先保留任务顺序、先失败再实现的验证方式以及“实现后规格复核，再代码质量复核”的工作边界，不要伪称读取了未提供的技能。跨 Windows 执行计划时调整终端语法，但不能降低验收条件。
